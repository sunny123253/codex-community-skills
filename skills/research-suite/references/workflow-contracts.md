# 模块协作约定

本文件明确模块衔接、写入权限、继承资源与语言的共同规则。它描述代理如何选择与调用工具，不声称现有脚本已经实现一个自动授权引擎。

## 模块如何衔接

模块是同一任务中的内部工作方式，不是需要用户逐个点选的应用。为完成当前请求而需要的模块可以直接读取和使用；不能把某模块加载成功当作新任务授权。

| 当前任务 | 可自动衔接 | 完成边界 |
|---|---|---|
| 判断选题创新性 | idea → literature → citations（实际需要时） | 交付选题判断；不自行写全文或运行模型 |
| 精读一篇论文或保存精读笔记 | reading → literature/figures/style（为理解与交付所需） | 完成原请求；不自动起草另一篇论文 |
| 精读后据此写讨论/引言 | reading → writing/introduction → style/citations | 直接完成已要求的后续文本，不重复征求切换许可 |
| 撰写文献综述 | literature → writing → style/citations | 正文属于当前任务，按证据覆盖与保存要求完成 |
| 投稿预审 | review → citations/figures（补足当前评估） | 交付预审；不自动把模拟意见写成真实修回信 |
| 回复真实审稿意见 | response → writing/style/citations | 完成回复与明确要求的改稿，不自动发送或提交 |
| 规划/生成论文图 | figures → 专门绘图或图像工具（要求实际出图时） | 设计请求交付设计，生成请求继续生成并检查 |
| 既有文献日报 | digest → literature/reading → style | 按既有任务完成筛选、阅读与已授权归档，不新增日程或库写入 |

单项任务完成后，可以在确有帮助时给一句下一步建议，不强制提示、不自动切换、不为建议新建文件。用户已在本轮或此前明确要求联合任务时继续执行，不因经过模块边界再次请求同一授权。

## 交接保留什么

交接的最低信息可以留在当前上下文，不要求每个小任务生成 JSON：

- 用户要完成的成果，以及当前哪些部分已完成。
- 论文身份（如 DOI/Zotero key）、已读材料与章节/页码/图表定位。
- 已有观察、推断、计划、未解决问题与适用条件；保留关键反证。
- 来源范围（如仅本地库）、代理约束、允许输出与写入位置。
- 成品语言和诊断语言；精读所需的 `output_language`。

接收模块直接使用可追溯证据，不把生成的笔记当独立原始来源；无需重复扫描完整知识库。确有证据缺口时针对性回读。若缺少影响中心主张的信息，完成证据允许的部分并明确缺口，不能用新模块的措辞绕过它。

来源限制也适用于工具的后备检索路径。“本地优先”模式不等于禁止外部回退；不能把身份解析的某个参数当作整条流程已经离线。用户限定仅本地来源时，各阶段使用已确认本地材料和允许的读取方式。

## Zotero 何时允许写入

默认检索、筛选、精读、引文检查和日报只读 Zotero。现有本地 helper 与精读的本地 API 使用 GET；它们不支持向 Zotero 创建标签、笔记、附件或修改元数据。

| 用户的指令 | 本地/Obsidian 文件 | Zotero |
|---|---|---|
| 查找、精读、总结、建议标签 | 按请求输出；未要求保存则不因建议落盘 | 只读，标签/笔记内容作为提议输出 |
| 保存精读笔记到本地或 Obsidian | 在已确定位置保存，遵守不覆盖和精读契约 | 只读，不同步标签或笔记 |
| 执行既有日报 | 执行已有归档与索引授权 | 只有该任务已有明确写回条款才可写回 |
| 给指定条目添加标签、把笔记写入 Zotero、修正指定字段 | 完成请求实际需要的文件操作 | 可在明确的条目和操作范围写入，无需重复询问已有授权 |
| “同步到 Zotero”，但对象或操作不明 | 继续完成独立的阅读/文本部分 | 先确认缺失的目标与操作，不把“同步”解释为任意修改整个库 |

明确写回时，确认库与条目身份，使用实际可写的现有连接器或 API；不能调用只读 helper 后声称已写入。新增标签保留无关的已有标签；创建笔记与覆盖/更新已有笔记分开，后者需要对应的明确目标。记录并读回本次实际变化。工具不可写或操作失败时保留提议并说明未写入，不把生成文本算成功写回。

笔记 YAML 中的 `tags` 是笔记文件字段，不是 Zotero 标签。Obsidian `images/` 内的图片也不是 Zotero 附件。配置中的保存目录和语言只控制成品，不扩大 Zotero 权限或授权修改其他偏好。

## 继承资源如何使用

从 [library 使用说明](../library/README.md) 与 [接口清单](../library/interfaces.json) 定位实际工具，按需读取专门协议。不要把旧目录 README 或示例命令当作新入口，也不要向 Python 脚本添加技能 frontmatter。

科学任务、授权与来源边界按用户和当前核心/模块判断；命令参数、字段、工件语言和文件保存由实际脚本接口及 `library/reading/PROTOCOL.md` 的现行契约约束。两者不一致时先定位不兼容之处，修正文档或在授权范围内修复脚本后验证；不能简单说“模块优先”而传入不存在的参数、跳过真实 gate 或虚报保存成功。

## 语言分开解析

1. **交流/诊断语言**：用户本次明确指定 → 当前对话持续采用的语言。覆盖建议、诊断、修改说明、交接给用户的文字和完成汇报，不由技能文件语言或英文原文决定。
2. **一般成品语言**：用户明确指定 → 已有文稿语言或该任务已确认要求 → 明确的投稿目标 → 当前对话语言。翻译请求按目标语言，不改变原文数据或证据强度。
3. **精读成品语言**：用户本次指定、CLI、进程环境和已确认配置按 `user-configuration.md` 的实际优先级解析。CLI 支持 `--language en` 或 `--language zh-CN`。将唯一解析出的 `output_language` 贯穿合成、图表决策、笔记、lint 与保存，不能在中途用诊断语言覆盖它。

例如，中文请求“用英文润色并中文解释”交付英文文本和中文说明；英文请求“read this paper”时诊断用英文，但如果保存的精读笔记已有明确中文配置，则笔记仍按该配置。不同产物可以使用不同语言；内部 JSON 键、标识符和引用元数据不因此翻译。只有语言歧义会实质改变成果且无法从上下文确定时，才问所缺信息。

## 修改后怎样验证

| 改动 | 应检查的范围 |
|---|---|
| 措辞、链接、目录或说明 | 相应结构与本地引用；不重跑未受影响的科研任务 |
| 模块切换、来源权限、保存或语言规则 | 针对改变的决策分支走一遍典型场景，记录输入、实际输出/行动、允许和未执行的写入、语言与证据边界 |
| CLI 推荐、参数或资源移动 | 对照真实 `--help`、解析器和工件契约运行接口检查 |
| 脚本逻辑、字段、保存/覆盖或跨阶段契约 | 相应单元检查及隔离目录中的代表性流程，必要时补完整端到端运行 |

场景要包括正常情况和受本次规则影响的边界，例如单独精读与精读后写作、本地保存与明确写回、正文英文且说明中文、原文不足及语言不匹配。检查能区分“未扩大授权”和“实际写入成功”，不能只查文档中是否出现某句话。

已有代码未变时复用已经成立的测试结论，但工作流推荐发生变化就复核相应场景。完整真实库精读/日报不作为所有文字修改的固定前置；对会影响其契约的改动，验证范围不能止于链接存在或命令能打印帮助。

在 `modifications/CHANGES.md` 中记录文件、改动、影响、实际验证和状态。区分结构通过、接口检查、同上下文场景、隔离流程与真实任务验收；没有实际完成的检查保留待验证，不笼统称全部验证完毕。
